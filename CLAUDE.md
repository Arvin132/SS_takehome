## What this is

This is a take-home assessment build: **SwishOS Stage 2 — Fleet Soiling & Cleaning Advisor**
(`swishsolar_round2_take_home_assessment.pdf` has the full brief). Read that PDF first if it's
still present — it is the spec; nothing below overrides it.

In short: solar plants accumulate "soiling" (dust/dirt) that reduces energy output. Rain or a
paid cleaning crew resets it. The system must turn per-plant telemetry into a recommendation of
which plants are worth cleaning today, let a human (asset manager / crew lead) act on that
recommendation, and use an LLM somewhere justified.

Key domain formula (from the brief, in `daily.csv` / `plants.csv` terms):

```
recoverable_usd = (expected_energy_kwh * soiling_loss_pct / 100)
                   * tariff_per_kwh
                   * days_until_next_reset
                 - cleaning_cost_usd
```

`days_until_next_reset` comes from `plants.csv`; rainfall forecasting is out of scope (use the
column as-is).

Every non-obvious implementation choice belongs in `DECISIONS.md` (Decision / Rejected / Cost /
Falsifier), plus a list of unverified assumptions — this file is read before the code and is part
of the deliverable.

**`DECISIONS.md` is off limits to agents. Never create, edit, or delete it — not to add a row,
not to fix a stale line, not even when a task says to keep it updated.** It is written by hand,
by the repo owner, and that authorship is the point: it is the deliverable that shows a human's
reasoning. When you make a decision that belongs in it, report the decision, what you rejected,
its cost, and its falsifier in your reply, and let the owner write the row.

  `PlantDayAiSummary`, plus `analytics/mine/` and the per-plant AI summary endpoint). Seed the DB
  with `python manage.py seed_fleet_data` (wraps `seed_data.py`, then loads the CSVs into
  Postgres and creates pre-determined accounts — see that command for the dev login,
  `admin`/`solar123`). `backend/db.sqlite3` and `backend/venv/` are still local-only artifacts,
  now vestigial since the DB is Postgres (see below) — don't rely on the sqlite file.
- `frontend/` is a real app (`react-router-dom`, `AuthProvider`, `AppShell`, `DashboardPage`,
  `PlantDetailPage`, `CrewDetailPage`, `AnalyticsPage`), not the template placeholder.
- `backend/Dockerfile` and `frontend/Dockerfile` both exist; `docker compose up --build` works
  end-to-end (db + backend + q2_worker + frontend).
- Root `README.md` exists and documents how to run both halves from a clean clone (Docker and
  native paths, ports, env vars). Keep it in sync with reality when architecture changes.
- `data/` (checked in) is a pre-generated sample dataset from `seed_data.py`'s default run (12
  plants × 120 days). Treat it as fixture data — `seed_fleet_data` regenerates it fresh (dated
  relative to "today") rather than reading the checked-in copy, since `days_until_next_reset`
  math is date-relative.

## The dataset

Generated by `seed_data.py` (stdlib-only, deterministic per `--seed`):

```
python seed_data.py                                          # 12 plants x 120 days -> ./data
python seed_data.py --plants 200 --days 540 --out data_scale # larger fleet, ~530MB, several min
```

Do not commit output of the scale run. Files under `data/`:

- `daily.csv` — one row per plant per day: `energy_kwh`, `expected_energy_kwh`, `pr`
  (performance ratio = actual/expected), `soiling_loss_pct` (blank when no clean baseline exists
  yet). **Start here** — this is the primary input for the recommendation logic.
- `plants.csv` — one row per plant: `capacity_mw`, `tariff_per_kwh`, `cleaning_cost_usd`,
  `days_until_next_reset`, `commissioned_on`.
- `events.csv` — one row per plant per day: `rain_mm` (≥~8mm washes panels clean), `cleaned`
  (0/1, whether a crew cleaned that day).
- `crews.csv` — `mw_per_day` (cleaning throughput), `day_rate_usd` (crew cost/day).
- `readings/plant_<id>.csv` — raw 15-minute telemetry that `daily.csv` is derived from; shouldn't
  be needed for the app logic.

The dataset has **deliberate data-quality defects** (gaps, stuck sensors, timezone shifts,
negative spikes — see `simulate_plant()` in `seed_data.py` for exactly which plants/rows are
affected via the modulo conditions on plant index). Don't assume clean input when writing
ingestion/aggregation code.

## Architecture direction (per docker-compose.yaml)

Four services:

- **`db`** — PostgreSQL 16. **Deviates from the brief's original SQLite-only, no-external-deps
  plan** — this should have a `DECISIONS.md` row (decision/rejected/cost/falsifier); don't
  silently revert it back to SQLite without that being addressed first.
- **`backend`** — Django + Django REST Framework API (`backend/solar/`), served via
  `manage.py runserver` (dev) / gunicorn (prod path implied by `reqs.txt`). Startup command runs
  `migrate && createcachetable && bootstrap_schedule && runserver`.
- **`q2_worker`** — Django-Q2 (`manage.py qcluster`) background worker/scheduler, using the
  database itself as the task broker (see `DECISIONS.md`: chosen over Celery+Redis for
  simplicity, at the cost of DB polling overhead and no multi-worker task coordination).
- **`frontend`** — Vite/React/TypeScript dev server, talks to the backend via `VITE_API_URL`.

Note the brief suggests FastAPI + React/Next.js as the "house" stack, but this repo uses Django +
DRF + Django-Q2 instead — a deliberate deviation that should be justified in `DECISIONS.md`, not
silently reverted.

LLM stack is in `backend/reqs.txt`: `langchain`, `langgraph`, `langchain-google-genai`,
`pydantic`. Implemented as `analytics.PlantDayAiSummary` / `PlantAiSummaryView`, generated by the
`q2_worker` via `GEMINI_API_KEY` (+ `GEMINI_MODEL`, default `gemini-2.5-flash`) read from a root
`.env` (gitignored). The system still runs end-to-end without that key configured (per brief) —
absence degrades the feature to a "failed" summary row instead of breaking anything else. Follow
this same gating pattern for any further LLM-backed feature.

Other architectural decisions already made (see `DECISIONS.md` for full reasoning — extend it,
don't contradict it silently):
- Simplistic auth: pre-determined users, scoped to specific plants (no signup flow).
- Django's DB-backed cache framework (`createcachetable`) instead of Redis.
- Crews are region-scoped, not global — a crew only services plants in its assigned region.

## Commands

**Full stack** (recommended — see root `README.md` for the full walkthrough):
```
docker compose up --build
docker compose exec backend python manage.py seed_fleet_data   # first run only
```
db on :5432, backend on :8000, frontend on :5173. Requires those three ports free. Optional
`.env` at repo root with `GEMINI_API_KEY` to enable the AI summary feature.

**Backend** (from `backend/`, with a venv active — one exists at `backend/venv/` but treat as
disposable/local, recreate if in doubt; requires a reachable Postgres instance, see
`DB_NAME`/`DB_USER`/`DB_PASSWORD`/`DB_HOST`/`DB_PORT` env vars in `solar/settings.py`):
```
pip install -r reqs.txt
python manage.py migrate
python manage.py createcachetable
python manage.py bootstrap_schedule
python manage.py seed_fleet_data            # loads/regenerates fixture fleet data
python manage.py runserver 0.0.0.0:8000    # API
python manage.py qcluster                   # background worker (separate process)
```

**Frontend** (from `frontend/`):
```
npm install
npm run dev        # Vite dev server, default port 5173
npm run build       # tsc -b && vite build
npm run lint         # eslint .
npm run preview
```

**Regenerating raw CSVs directly** (only if intentionally changing the dataset shape — prefer
`manage.py seed_fleet_data` for anything that needs to end up in the DB):
```
python seed_data.py
```
